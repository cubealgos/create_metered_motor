## Scope

The trades (`ARCH-DEC-004`): three villager trade files under `data/metered_motor/villager_trade/toolsmith/<level>/emerald_metered_motor_<tier>.json` (`TRADE-REQ-001`), the tag entries appending each to `data/minecraft/tags/villager_trade/toolsmith/level_<n>.json` with `replace: false` (`TRADE-REQ-003`), the `metered_motor:roll` loot function type reading tier and the three bands (rpm, capacity, efficiency) from the trade file and writing the `metered_motor:stats` component with uniform rolls from the loot context's random source (`TRADE-REQ-002`), the `metered_motor:no_motor_offered` merchant predicate (a loot condition) so a villager's later-level draw skips the trade once it already offers a motor (`TRADE-REQ-006`, `TRADE-DEC-004`), and the tooltip showing rolled stats before purchase (`TRADE-REQ-005`, `UI-REQ-006`).

## Approach

First step: verify whether 26.2's `merchant_predicate` loot condition type sees the villager entity and its current offers when a level's trades are drawn (the spec's open question, `docs/spec/domains/trade.md` §7) — read the loot condition's context parameters and, if it does, write `metered_motor:no_motor_offered` against them directly; if it does not, fall back to a villager-level hook (an entity-level check before the trade set draws) and record which path was taken and why in this ticket. Then the three trade files and tag entries as plain data, and `metered_motor:roll` as a `MapCodec`-registered `LootItemConditionalFunction` (spec `README.md` Verification 6) parameterised by `{tier, rpm: {min,max}, capacity: {min,max}, efficiency: {min,max}}`, rejecting an out-of-range band per `TRADE-REQ-004` and falling back to the tier's default.

## Acceptance criteria

- [ ] The finding on whether `merchant_predicate` sees the villager and its offers is recorded in this ticket's Constraints section before the loot condition is written.
- [ ] Game test: the three trade files parse through the recipe/loot manager and the tags contain their paths (`TradeFileGameTest`).
- [ ] Game test: a mock toolsmith offer carries a roll inside its tier's band for rpm, capacity and efficiency (`RollGameTest`).
- [ ] Game test: a villager already offering a motor does not draw a second at a later level (`NoDuplicateOfferGameTest`), exercising whichever mechanism the first step settled on.
- [ ] Game test: a band whose minimum exceeds its maximum, or that leaves the tier's documented range by more than a factor of four, is rejected and the tier's default band is used instead, logged once (`TRADE-REQ-004`).

## Findings

**`merchant_predicate` does see the villager entity and its live offers; no villager-hook fallback is needed.** Read against the merged-deobf 26.2 jar: `VillagerTrade.getOffer(LootContext)` tests `merchantPredicate` (the `Optional<LootItemCondition>` decoded from `merchant_predicate` via `LootItemCondition.DIRECT_CODEC`) directly against the `LootContext` it is called with, returning `null` (no offer) on failure before running `given_item_modifiers`. `AbstractVillager.addOffersFromTradeSet(ServerLevel, MerchantOffers, ResourceKey<TradeSet>)` builds that `LootContext` from `LootContextParamSets.VILLAGER_TRADE` (whose three params — `ORIGIN`, `THIS_ENTITY`, `ADDITIONAL_COST_COMPONENT_ALLOWED` — are all `required`, confirmed from the param set's bootstrap lambda), setting `THIS_ENTITY` to the villager itself (`this`) and passing the `MerchantOffers` from `getOffers()` — the villager's own live, mutable offer list, not a copy — into `addOffersFromItemListings`/`addOffersFromItemListingsWithoutDuplicates`. Both of those methods append each drawn trade's `MerchantOffer` to that same list immediately, one trade at a time, before drawing the next; `Villager.updateTrades(ServerLevel)` passes `getOffers()` into `addOffersFromTradeSet` on every level-up, so a later level's draw sees every offer from every earlier level, and even a second trade in the *same* level's two-trade batch sees the first if it went in ahead of it. So a merchant predicate that reads `((Merchant) context.getOptionalParameter(THIS_ENTITY)).getOffers()` sees exactly the offers made so far, in real time, with no special-cased "current offers" context param and no mixin needed. `metered_motor:no_motor_offered` (`metered_motor.trade.NoMotorOffered`) implements this directly.

**Cross-ticket note for MM-3 (recorded, not a criterion):** the trade files correctly give `metered_motor:metered_motor` (`TRADE-REQ-001`, `contracts/public-surface.md`), but that item does not exist on this branch. 26.2's registry loader resolves an `ItemStackTemplate`'s `id` at *datapack-load* time via a strict registry-key codec (not the item registry's runtime `DefaultedRegistry` fallback), so an unresolved `gives.id` is a hard parse failure for that `villager_trade` element; `MappedRegistry.freeze()` then refuses the entire `minecraft:villager_trade` registry over the unbound entries, and that failure propagates through `minecraft:root`, so the *whole* data pack fails to load and the game test dedicated server cannot start at all — not a soft, per-trade failure. Confirmed by temporarily registering a throwaway placeholder `Item` under `metered_motor:metered_motor` (not committed): with it present, all 8 `@GameTest` methods pass, including the TRADE-REQ-004 malformed-band fallback and its log line. Without MM-3's item, `just gametest` (and therefore `just check`) cannot pass on this branch in isolation; this is expected to resolve once MM-3 merges and is not a defect in this ticket's code. A placeholder registration was deliberately not committed, since it would collide with MM-3's own `metered_motor:metered_motor` item registration at merge time (a silent runtime crash on the shared registry id, not something a git merge would catch).
